# Надёжность RemoteVoice

Текущий проверенный Host — **0.1.18**, Android остаётся **0.1.20**. Сеть, которая перестала передавать данные при открытом TCP, вернула все физические роли за 4,599 с; падение Voicemeeter — за 1,492 с; авария Host — за 0,583 с. Исходный ручной mute сохранён. Обычный сеанс после автоматического запуска микшера вернул устройства за 0,959 с. 376 Python-тестов и packaged guard прошли. Это отдельные измерения, не гарантированные максимумы.

Host и guard запущены через фактический desktop-объект Explorer и пережили завершение kill-on-close группы процесса запуска. Проверяется принадлежность именно этой группе: системная Windows job у Explorer может существовать и сама по себе не означает зависимости от Codex. Конфигурация и сопряжение скопированы из MSIX-перенаправления в собственный Roaming-профиль RemoteVoice с сохранением предыдущих файлов; секреты не включены в отчёты. Неисправный сетевой путь и принудительное закрытие Host — разные сценарии, оба проверены. Результаты — `.harness/evidence/startup-cursor/`.

Видео остаётся незавершённой задачей: JPEG всё ещё недостаточно плавен, новый H.264-профиль по умолчанию отключён. Исправление флага захвата курсора покрыто проверками native-вызовов, визуальная приёмка ещё нужна. Следующие абзацы содержат исторические срезы.

## Что изменилось

- Один Host владеет устройствами: блокировка приобретается до восстановления и настройки. Второе окно не переключает живой сеанс.
- Подключение подтверждается после подготовки mute, виртуального входа и выхода. Ошибка любого шага откатывает остальные; исходная ошибка остаётся видимой.
- Живые аудиопотоки сохраняются в учёте. Незавершённая остановка запрещает конфликтующий новый сеанс. Старт и прогресс нативного движка имеют контроль времени; возврат устройств не ждёт его остановки.
- Независимый guard ждёт смерть конкретного Windows process HANDLE, получает исключительную блокировку и восстанавливает input/output/mute. Обрыв pipe сам по себе не даёт права менять устройства. Отказ guard во время живого сеанса также останавливает его с возвратом ноутбука.
- Android учитывает прогресс и возраст очереди вместо ожидания полного `queueSize=0`. Пределы памяти и свежести сохранены; устаревший голос не накапливается. Mute/ACK и безопасный отказ остаются обязательными.
- Busy/stop не расходуют PIN; некорректные credentials и NaN/Inf контролируемо отклоняются. Retry просмотра экрана сопоставляется по строковому request ID.
- Для iPhone внесены strict IPv4, ограниченный writer, ACK перед capture, unwind аудиостарта, MainActor/generation/cancellation и единый terminal cleanup. Компиляция и runtime ещё не выполнены.
- LocalSign использует один staged IPA с проверенным hash; Windows handle запрещает его изменение до окончания операции. Неизвестная установка сохраняет effect ID и блокирует автоматический повтор. Ручное решение пользователя хранится отдельно и не запускает повторную установку.

### Возврат устройств Windows

Проверялся идентифицированный Host из отдельного снимка исходников через обычный `launcher.py`, без подмены UI обработчиков. Во всех трёх сценариях все роли ввода/вывода вернулись на Realtek, исходный mute=False сохранился; телефонный микрофон не включался, аудиокадры не сохранялись.

| Сценарий | Время подтверждённого возврата |
| --- | --- |
| Обычное закрытие соединения | 0,934 с |
| Аварийный разрыв транспорта | 0,863 с |
| Принудительное завершение Host, recovery отдельным guard | 1,368 с |

После crash Host перезапущен. Результаты привязаны к исходникам и startup receipt в локальной папке `.harness/evidence/reliability/`. Пользователь затем подтвердил минутную проверку Android: «Всё работает и вернулось». Исходно заглушённый микрофон, более длительная речь, фон и блокировка остаются отдельной приёмкой.

После пользовательского теста чтение Windows подтвердило физические роли ввода/вывода и mute=True. Пользователь уточнил, что выключил микрофон вручную. Этот ручной выбор сохранён; ошибочное предположение дополнительной пробы о mute=False не считается отказом восстановления.

## Перед публичным выпуском

1. Подтвердить длительную речь, mute, блокировку/фон, смену аудиовыхода и повторное подключение на телефоне; проверить дополнительные негативные сценарии Windows.
2. Собрать Swift на macOS и выполнить fixtures/fault tests, затем подписать и проверить реальный iPhone. По решению пользователя работа пока локальная; исходники в GitHub не отправлены и CI не запускался.
3. Локальный Windows EXE собран в формате папки приложения. Guard из EXE прошёл handshake/disarm и ожидание смерти тестового владельца с отказом от записи при занятой блокировке. Полная аудиосессия из EXE, чистая установка/удаление и обновление остаются отдельной приёмкой; работающий Host из исходников не заменён.
4. Выбрать постоянную signing identity Android, проверить два чистых подписанных build и обновление без удаления данных. Приватный ключ не хранить в Git.
5. Закрыть настройки, лицензии и платформенные условия распространения. Публикация и покупки выполняются отдельно. Свой Anisette, renewal и LocalSign Store также остаются самостоятельными обязательствами.

Физический обрыв сети прерывает передачу; бесконечная очередь не исправляет его. Требование версии — контролируемый отказ, подтверждённый возврат ноутбука и явный статус. Нельзя гарантировать восстановление при одновременной остановке Host и guard, сбое ОС или недоступном драйвере. Эти ограничения не выдаются за пройденные сценарии.

## Дополнительная локальная проверка Windows-пакета

PyInstaller 6.22.3, Python 3.14.4: сборка `onedir/windowed` прошла. Для frozen guard явно задан `PYINSTALLER_RESET_ENVIRONMENT=1`, чтобы процесс восстановления имел независимую среду. `onedir` исключает дополнительный процесс распаковки `onefile` и позволяет останавливать именно процесс helper. Обоснование: [документация PyInstaller](https://pyinstaller.org/en/latest/common-issues-and-pitfalls.html).

После изменения повторно прошли 260 тестов Host. Из собранного EXE проверены готовность за 1,003 с, штатный disarm, ожидание завершения отдельного тестового владельца и отказ менять устройства при занятой блокировке. Тестовые процессы завершились. Реальные аудиомаршруты этой проверкой не изменялись. Результаты и хэши полного пакета находятся в `.harness/evidence/windows-package/`. Проверки предыдущего снимка исходников сохранены как история; текущий EXE не объявляется принятым по старым нативным проверкам.

## Приёмка возврата устройств из EXE

23 октября 2026: обычное закрытие соединения, аварийный разрыв транспорта и принудительное завершение идентифицированного EXE вернули все физические роли ввода/вывода и исходный mute=False за 1,143 / 1,154 / 0,898 с соответственно. Guard подтвердил восстановление после аварии; EXE перезапущен. Это контролируемые локальные соединения без включения телефонного микрофона. Android-фон/блокировка и длительная речь остаются открытыми.

Первый запуск EXE остановился на ошибке отсутствующего работающего Voicemeeter Banana. Диагностический стек показал ожидание окна ошибки, API Login вернул 1. После запуска уже установленного Banana тот же EXE открыл порт и прошёл три проверки. Диагностические процессы закрыты. Пользователю требуется работающий Banana; автоматический запуск зависимости пока не реализован.

## Понятная причина отказа запуска

В исходниках после нативной диагностики добавлены отдельные сообщения о незапущенном микшере и неподходящей версии Voicemeeter. Статус Host сохраняет причину после закрытия окна ошибки, а само окно привязано к Host. Проверки дополнены условиями: при этих отказах параметры микшера не записываются, listener не открывается, logout выполняется. Все 260 тестов Host и compileall прошли.

Отдельная сборка `host/build/startup-feedback/dist/RemoteVoice/` собрана; реальный helper из неё подтвердил готовность и disarm за 1,028 с, ожидание смерти владельца и запрет восстановления при занятой блокировке. Работающий сеанс использует ранее проверенный EXE. Приёмку аудио и проверки остановленного микшера для новой сборки нельзя считать выполненными по старым наблюдениям; хэши снимков хранятся раздельно.
