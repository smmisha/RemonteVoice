# Исследование пауз Wi-Fi

Проверено 27 октября 2026 года. Исходники, EXE и APK в этих проверках не менялись. Подтверждённого исправления Wi-Fi пока нет.

## Что установлено на устройствах

- Windows: MediaTek MT7922/RZ616, драйвер 3.6.2.1434. Эта версия присутствует на [странице ASUS FA608PM](https://www.asus.com/us/supportonly/fa608pm/helpdesk_download/). Драйвер не скачивался и не переустанавливался.
- Windows использует websockets 17.2, SoundCard 0.4.6 и NumPy 2.5.3; Android использует OkHttp 4.12.0 и Android API 31.
- Единственный изменяемый кандидат для следующего отдельного теста — имеющаяся настройка адаптера `Power Saving`, ключ `LowPowerEnable`: сейчас `1`/Auto; драйвер сообщает допустимый вариант `0`/Выключено. Значение Auto не доказывает, что радио фактически спало во время сбоя.

## Новые измерения

### 311: без аудиосеанса

В короткой выборке Windows → телефон: 40/40 ответов, максимум 221 мс, среднее 74,125 мс. Windows → роутер: 40/40, максимум 135 мс, среднее 38,875 мс. Телефон → роутер: максимум 92,5 мс, среднее 13,636 мс. ICMP не является измерением звуковой задержки.

### 312: повторное воспроизведение с сетевым наблюдением

Проблема повторилась: 45 underrun, 40 rebuffer, максимум интервала приёма 589 мс; сеанс закрылся с 1011, 240-секундный сигнал не завершился. Потерь очереди не зарегистрировано. Windows восстановила исходные шесть ролей и mute. Считать этот прогон успешным нельзя.

Вся завершённая часть trace содержит 5695 пакетов без пропуска раннего окна. Максимумы: захват 20,017 мс; dispatch 1,946 мс; ожидание send lock 0,077 мс; выполнение send 913,596 мс; интервал завершённых отправок 925,717 мс. TCP-оценка RTT достигала 775,508 мс, счётчик retransmit менялся. Это связывает проблему с ожиданием транспорта, но не разделяет радиопомехи, адаптер, AP и системное планирование.

Windows ICMP-наблюдатель: 57/60 ответов телефона, максимум 724 мс; 60/60 ответов роутера, максимум 711 мс. Телефон → роутер: максимум 214 мс. Наблюдатель продолжал работу после остановки аудио, поэтому его общие максимумы нельзя автоматически приписывать моменту остановки. Дополнительная грубая привязка Windows UTC к monotonic-окну завершённых отправок с отступом 300 мс сохраняет эти максимумы: для телефона 31 ответ и 2 таймаута, для AP 33 ответа. Эта привязка предполагает отсутствие скачка часов; субсекундная причинность не заявляется.

Idle и active наблюдения имели разный интервал запросов. Это диагностические выборки, а не контролируемый A/B-тест воздействия Wi-Fi lock или аудиопотока.

## Следующее проверяемое действие

Выполнен согласованный [план проверки энергосбережения](WIFI-POWER-SAVING-TEST-PLAN.md) с возвратом исходной настройки. Исходный документ перед изменением статуса сохранён как `wifi314-approved-plan.md` и соответствует хешу из prepared manifest. Отключение энергосбережения не принято как исправление. Другие драйверные настройки, диапазон, роутер и таймауты не менялись.

| 317 | Auto, без дополнительного переподключения адаптера | Полные 240 секунд / 11 520 000 render-кадров и два фоновых интервала; 0 dropped/underrun/rebuffer, максимум приёма 233 мс | 60/60, максимум 22 мс, среднее 3,467 мс |

315 сохраняется как неуспешная попытка, его частичные нулевые счётчики не принимаются за успех. Его elevated-runner имеет `completed=false`, `rollback_verified=true`, `audio_matches_baseline=true`; этот файл не перезаписывался. В замещающем контроллере 317 добавлен единственный повтор read-only logcat или идемпотентного force-stop своего приложения через 250 мс. Сетевой и аудиокод приложений не менялись. 314 выполнялся временным elevated-runner, 317 — обычным процессом; это дополнительное различие измерительной среды, которое также не позволяет выдавать последовательное сравнение за строгое доказательство причины.

Таким образом, отключение энергосбережения не является необходимым условием наблюдавшегося улучшения. Перезапуск адаптера или изменение условий могли повлиять, но эксперимент не различает эти версии. Разовый успешный Auto 317 не отменяет предыдущий воспроизведённый отказ Auto 312 и не подтверждает исправление для длительной работы.

Для дальнейшей диагностики прочитаны только численные метаданные журнала WLAN без сообщений/SSID/MAC и два штатных параметра WlanQueryInterface. API-запрос показал `background_scan_enabled=true`, `media_streaming_mode=false`, вызовы завершились успешно и handle закрыт. Microsoft [описывает этот режим](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/ne-wlanapi-wlan_intf_opcode) как режим для медиапотока, учитывающий клиентов и автоматически сбрасываемый при отключении интерфейса. Сам режим не включался, сканирование не отключалось; причинность и полезность такого эксперимента пока не проверены. Разрешение PERM-033 относилось только к завершённому тесту LowPowerEnable.

Финальный readback 318: исходные шесть ролей Windows/mute, Auto=1, прежние EXE/APK, обычные Host 24104/guard 43712 без opt-in trace/compression, нет аудиосеанса и тестовых процессов. Wi-Fi более не переподключался в замещающем тесте. Пользователь отдельно выразил недовольство сетевыми прерываниями; момент любых будущих действий, влияющих на связь, следует явно объявлять заранее.

Следующий шаг — усилить наблюдаемость точной причины закрытия 1011 и сопоставить WLAN/транспортные события при новом воспроизведении. Новые системные изменения без согласованного конкретного шага не планируются; прикладной код и нормальный запуск можно диагностировать отдельно.

Доказательства находятся в `.harness/evidence/integrated-audio/`: `wifi311-idle-network.json`, `wifi312-active-network.json`, `wifi312-locks.json`, `real-audio312-phone-run/`, `audio312-sustained-summary.json`, `wifi313-coarse-window.json`, `wifi313-adapter-preflight.json`, `usb313-final-state.json`, `wifi314-ab-run/`, `real-audio314-phone-run/`, `real-audio315-phone-run/`, `real-audio317-phone-run/`, `wifi314-active-network.json`, `wifi317-active-network.json`, `wifi318-wlan-event-scalars.json`, `wifi318-wlan-query.json`, `usb318-final-state.json` и `wifi318-final-power.json`. Host и APK восстановлены в обычное состояние; микрофон автоматически не включался; PCM и изображения не сохранялись.
