## Реализованный локальный этап

В исходниках Host добавлен `audio_backend.py`: подготовка выбранной пары и проверка доступности вынесены из HostWindow. Существующая настройка Banana и обычных выбранных виртуальных пар сохранена. Отказ подготовки останавливает старт сервера; ошибка проверки здоровья вызывает существующее восстановление всех управляемых маршрутов. Это подготовка интерфейса замены, а не новый драйвер. Рабочий EXE 0.1.22 не обновлялся.

`host/native_audio` содержит собственный in-process duplex PCM DLL-прототип. Два независимых SPSC-буфера для stereo render и mono mic имеют фиксированные границы, проверку размеров/finite, поколение сеанса, явный close и пустое/закрытое чтение тишины. C++ read/write не выделяет память, не пишет журналы/файлы и не вызывает Windows audio. Нативные тесты проверили разделение каналов, полную очередь, старое поколение и 20 000 параллельно переданных пакетов в порядке. Ограничения lifetime и ABI — в `host/native_audio/README.md`. DLL не создаёт Windows-устройства и не загружается рабочим Host.

Установленные MSVC x64 и Windows SDK позволяют собрать этот user-mode прототип без установки дополнительных компонентов. Стандартный WDK-заголовок portcls.h отсутствует в проверенном SDK; сборка собственного аудиодрайвера пока не подтверждена.

## Целевая схема

- Единственное пользовательское приложение и владелец сессии — RemoteVoice. Сервер, кодировщик и восстановление управляются его жизненным циклом.
- Аудиокомпонент без отдельного окна и значка в трее предоставляет два независимых endpoint: виртуальный render для звука ноутбука и виртуальный capture для голоса телефона. Имя устройств относится к RemoteVoice.
- Render-поток поступает в сетевой передатчик; принятый голос телефона поступает только в capture. Обратная петля между этими направлениями исключается и проверяется сигналом.
- Существующие TLS-сопряжение, явное включение микрофона, подтверждение готовности воспроизведения, отдельный экранный канал и ограниченные очереди сохраняются.
- Переключение Windows выполняется только после готовности endpoint, рабочего аудиопотока и вооружённого помощника восстановления. До изменения сохраняются все роли input/output и исходный mute.
- Потеря связи, остановка приложения и подтверждённый отказ компонента прекращают сессию и восстанавливают сохранённые устройства. Новый backend не должен зависеть от отрисовки UI для передачи аудио. Старые журналы восстановления остаются совместимыми либо мигрируются проверяемо.
- Подготовка/здоровье/остановка backend выносятся в небольшой интерфейс. Существующие операции Windows route/guard не дублируются. Voicemeeter-adapter остаётся для сравнения до приёмки нового backend; в публичном варианте он не является обязательной зависимостью.

## Эксперимент с передачей PCM без потерь — 27 октября 2026
